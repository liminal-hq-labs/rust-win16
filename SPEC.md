# Rust Win16 specification

## Purpose

Build Windows 3.x programs in Rust: a code16 target, an NE packer and import stubs. Rust `no_std` code compiled for LLVM's `code16` mode is linked by `rust-lld` and rewrapped as a Win16 NE executable that Windows for Workgroups 3.11, Windows 9x and Wine load.

## Users and scenarios

- Someone writing a small native Windows 3.x program, such as an installer, a launcher or a utility, in Rust.
- Someone studying the NE format, the Win16 loader and the Pascal calling convention through a short, tested packer.
- A project that wants a Win16 runtime in Rust and needs the register and loader rules already settled.

## Non-goals

- Windows 3.1 Standard mode on a 286, and real mode. The code needs a 386 or later.
- Windows 3.0.
- A general Win16 SDK: the import table is small and grows by need.
- A C or C++ toolchain. Open Watcom already does that well.
- Icons, for now.

## Components

| Part | Path | Role |
|---|---|---|
| Target spec | `win16.json` | `i386-unknown-none-code16`, `rust-lld`, soft float, abort on panic |
| Linker script | `link.ld` | `.data` at address 0; every code section an output section of its own above 0x100000, with its relocations kept |
| Runtime | `src/lib.rs` | Task entry and the 32-bit stack alias, `export_proc!`, exit, panic and shadow-stack handlers, log buffer, helpers and Win16 structures |
| Import stubs | `src/imports.rs` | Generated by `tools/gen_imports.py` from `tools/imports.tbl`; do not edit |
| Modules | `src/wizard.rs`, `src/probe.rs` | A three-page wizard state machine and register probes |
| Packer | `tools/ne_pack.py` | ELF in, NE out: places code in segments, writes veneers and fixups, with resources and segments from JSON |
| Demangler | `tools/rust_demangle.py` | Rust symbol names to paths, for placement patterns and the map |
| Checker | `tools/ne_check.py` | Decodes every code segment and fails on a branch that leaves its segment |
| Fault lookup | `tools/ne_addr2sym.py` | A `segment:offset` from a fault box to a function, through the packer's map |
| Dumper | `tools/ne_dump.py` | An independent NE reader |
| Library runtime | `dll/src/lib.rs` | The `w16dll` crate: `LibEntry`, `WEP`, `export_dll!`, the private stack, the panic path and far-pointer helpers |
| Examples | `examples/{msgbox,hello,setup,bigseg,dllhost,hellodll}` | Programs and a library built by `scripts/build.sh` (`hellodll` is built by the `w16dll` package) |
| Tests | `tests/test_ne_pack.py`, `tests/test_segments.py`, `tests/test_library.py`, `tests/test_dll.py` | Packer, segment, library and generator tests |
| Windows 3.11 harness | `scripts/run-w31.sh` | Runs a program on a Windows 3.11 tree you supply, under DOSBox-X, and counts passing runs |

## Behaviour

- `scripts/build.sh` builds each example for the `win16` target with `RUSTC_BOOTSTRAP=1 cargo build --release`, then packs the ELF into `out/<NAME>.EXE` and its map into `out/<NAME>.MAP` (`OUT_DIR` moves them) with the module name set to the upper-cased example name, and `examples/<name>/segments.json` when there is one.
- A program defines `w16_main(hinst, hprev, show) -> u32` and links the `w16` crate. `_start` runs INITTASK first, makes a 32-bit alias of the stack segment through DPMI and moves to it, then calls `WaitEvent(0)` and `InitApp`, calls `w16_main` and exits through `w16_exit` (back to the 16-bit stack, the alias freed, INT 21h function 4Ch) with the result.
- Rust code runs on the 32-bit alias; Windows never does. Every API call goes through a generated stub that saves EBX, ESI, EDI and EBP, moves to the 16-bit stack for the far call, moves the alias to the data segment's current base if Windows moved it, moves back with ESP rebuilt from SP and reloads ES from DS.
- A window or dialog procedure is wrapped by `export_proc!`, which loads DS and ES from SS, saves the same registers, moves to the alias around a Rust function taking `(hwnd, msg, wparam, lparam)` and returns on the stack segment it was called on.
- The packer places code in segments (pinned sections in segment 1, then `.text.seg<N>` section names, then `--segments` patterns, then an automatic fill by budget), rewrites each call across segments to a veneer and a return trampoline with far fixups, sends tail calls and calls through function pointers into other segments through a shadow return stack in the data segment, gives each address-taken function a slot at the same offset in every segment, and sends every far entry into a load-on-call or discardable segment through a gate in segment 1. [docs/packer.md](docs/packer.md) describes each.
- With `--library`, the packer writes a DLL instead: single data (one moveable data segment shared by all callers), `LibEntry` as the entry point, no stack, exports at the ordinals the manifest fixes, `WEP` at ordinal 1 by default, and no Windows imports beyond the manifest's allow-list. EXE output is unchanged.
- A library defines its exports with `export_dll!(Name, rust_fn, words)` from the `w16dll` crate (`dll/`), which also provides `LibEntry`, `WEP` and the panic handler. `LibEntry` stores the instance handle, paints the private stack and returns 1. An export's thunk saves the caller's registers, loads DS from the library's data segment, refuses the call when the library is poisoned (status 7) or busy (2), makes the 32-bit alias of the data segment on the first call (status 6 when DPMI refuses) and moves it to the segment's base at every entry, copies the Pascal arguments (one zero-extended `u32` per word, first word first) to the top of a 6,144-byte private stack inside the data segment, switches to it and calls the Rust function, then returns far with the result in DX:AX. A panic poisons the library and returns status 7. `WEP` frees the alias and returns 1. A library calls nothing in Windows.
- A row `DYN LIBRARY ORDINAL Name ARGS RET` in `tools/imports.tbl` makes a stub that calls a library the program loaded itself, through a far pointer in the 4-byte slot `__w16dyn_<Name>` that `bind_<Name>` fills with the result of `GetProcAddress`; an empty slot returns `0xFFFF`. `docs/libraries.md` has the rules and the measurements.is not a 32-bit x86 ELF, a function is over 64 KB, a segment cannot be brought under 64 KB, data plus stack plus heap (plus the shadow stack) is over 64 KB, a reference to another segment cannot be made safe (an address inside a function taken from another segment, a relative reference that is not a call or a jump, a 16-bit call), an exported procedure is outside segment 1, a library's exports and its manifest disagree or share an ordinal, a library imports a Windows function that is not on its allow-list, a symbol is undefined, or the segments file is malformed. Each message names the symbol or the setting.

## Interfaces

**Packer.** `python3 tools/ne_pack.py [--module NAME] [--description TEXT] [--stack N] [--heap N] [--resources FILE.json] [--segments FILE.json] [--library MANIFEST.json] [--shadow N] [--map FILE] <in.elf> <out.exe>`. Defaults: module `SETUP`, stack 8192, heap 4096, shadow stack 256 entries. Symbols it reads: `_start`, `__w16imp_<MODULE>_<ordinal>_<Name>`, `__w16exp_<Name>`, `__w16sel_code_<n>`, `__w16sel_data_<n>`, `__w16sel_seg<N>_<n>`, `w16_shadow_overflow`, `__w16_ss16`, `__w16_ss32`, `w16_sync_alias`. See [docs/packer.md](docs/packer.md).

**Segments.** A JSON object with `segments` (keyed by code segment number, 1 or 3 to 254, each with optional `name`, `place` patterns, `budget`, `preload` and `discardable`), `auto` (`budget`, `preload`, `discardable` for automatically filled segments) and `shadow`. Patterns match demangled Rust paths and section names. Code segments are numbered without gaps.

**Library manifest.** A JSON object for `--library`: `module`, `description`, `heap` (default 0), `exports` (name to ordinal, or `{ordinal, words, shared}`), `gaps` (`allow` or `error`) and `imports` (`MODULE.Name` allow-list, default the four `KERNEL` `Global*` memory functions). The packer then writes a DLL: flags `0x8301`, `LibEntry` as the entry point, stack 0 and `SS:SP` 0:0, the exports at their fixed ordinals in segment 1, a resident `WEP` (a default that returns 1 when the program has none), and a refusal of any import off the list. See [docs/packer.md](docs/packer.md#building-a-library).

**Checker.** `python3 tools/ne_check.py file.exe` (needs `objdump`).

**Windows 3.11 harness.** `W31_TREE=DIR [DOSBOX_IMAGE=IMAGE] [OUT=DIR] [WAIT=S] [W31_NAME=PREFIX] scripts/run-w31.sh [--runs N] [--log NAME] [--with FILE]... [--system FILE]... PROGRAM.EXE [ARGUMENTS...]`. `--with` puts a file beside the program and `--system` in `C:\WINDOWS\SYSTEM`.

**Resources.** A JSON object with `dialogs`, `strings` and `rcdata`. Dialog IDs, string IDs and raw-data IDs are integers; `rcdata` entries name a file relative to the JSON. Raw data starts with its exact length as a little-endian 32-bit number.

**Import table.** One row per import in `tools/imports.tbl`: `MODULE ORDINAL Name ARGS RET`, where `ARGS` uses `w`, `l`, `p` and `f` and `RET` is `w`, `l` or `v`, or `DYN LIBRARY ORDINAL Name ARGS RET` for a dynamic import. `python3 tools/gen_imports.py [--check-spec DIR] tools/imports.tbl src/imports.rs` writes the stubs and checks them against Wine's spec files.

**Dumper.** `python3 tools/ne_dump.py [--json] file.exe`.

## Settings and defaults

| Setting | Default | Meaning |
|---|---|---|
| `--stack` | 8192 | Stack size in the data segment, in bytes |
| `--heap` | 4096 | Local heap size in the data segment, in bytes |
| `--shadow` | 256 | Shadow return stack entries (4 bytes each) in a program of several code segments |
| Automatic budget | 61440 | Bytes of code per automatically filled segment, before veneers |
| `--module` | `SETUP` | The module name written to the NE tables |
| `RUSTC_BOOTSTRAP` | `1` (set by `scripts/build.sh`) | Allows `-Zbuild-std` and a JSON target on the pinned stable compiler |
| `CARGO_TARGET_DIR` | `./target` | Where Cargo writes the ELF |
| `OUT_DIR` | `./out` | Where the NE executables go |

## Security and privacy

The tools read the files named on the command line and write the output path. They make no network requests; only `gen_imports.py --check-spec` reads spec files you have downloaded. The programs are as capable as any Windows 3.x program, since the system has no privilege boundary: the examples write only under `C:\W16TEST`, `D:\` and `A:\`.

## Limits

| Area | Limit or finding |
|---|---|
| CPU | A 386 or later in 386 Enhanced mode |
| Code | Up to 253 segments of 64 KB each, veneers and slot table included; a single function at most 64 KB; the file at most 1 MB |
| Calls across segments | Direct calls through stateless veneers; tail calls and calls through function pointers into another segment through a shadow return stack, 256 levels deep by default |
| Stack | Rust runs on a 32-bit alias of the stack segment made through DPMI; without DPMI it runs on the 16-bit one and is exposed to ESP's dirty high half |
| Placement | Exported procedures, import stubs and the runtime's fixed helpers are in segment 1 |
| Data, stack, heap | One segment (DS = SS), 64 KB in total |
| Pointers | Near pointers are 32-bit values with a zero high half; far pointers are built as `selector:offset` |
| Allocation | No global allocator; the `alloc` crate builds but is unused |
| Formatting | No `core::fmt` |
| Startup | INITTASK must be the first instruction run |
| Instances | `export_proc!` is untested with two instances |
| Verification | Wine, DOSBox-X with Windows for Workgroups 3.11, and Windows ME in a virtual machine; never real hardware. Several code segments and the 32-bit stack: Wine and Windows for Workgroups 3.11 under DOSBox-X only |
