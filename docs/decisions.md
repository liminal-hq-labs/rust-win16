# Decisions

Each decision is numbered and stays here even when superseded, with a note on what replaced it. Open questions move here once they are answered.

| # | Decision | Choice | Why |
|---|---|---|---|
| D1 | Home | A Liminal HQ Labs experiment in `liminal-hq-labs/rust-win16`, public from the first commit | Try the idea in the open before it earns a place in Liminal HQ |
| D2 | Licence | `Apache-2.0 OR MIT` | House licence, compatible with both ecosystems |
| D3 | Dependency updates | No Dependabot configuration until the project opts in | Labs repositories stay quiet by default. See the [Labs charter](https://github.com/liminal-hq-labs/.github/blob/main/docs/labs-charter.md#dependabot-is-opt-in) |
| D4 | Language and target | Rust `no_std` built for LLVM `i386-unknown-none-code16`, linked by `rust-lld`, rewrapped as an NE executable by our own packer | It gives 16-bit segments with 32-bit registers on a pinned, stock toolchain, and the same Rust code can share tooling with other projects. The cost is an unsupported use of LLVM that is meant for bootloaders |
| D5 | CPU floor | A 386 or later, in 386 Enhanced mode, with no Win32s | Rust code is full of operand-size and address-size prefixes, which a 286 treats as invalid opcodes. Windows 3.1 Standard mode on a 286 is out |
| D6 | Compiler and build | A pinned stable compiler (1.98.0) with `RUSTC_BOOTSTRAP=1`, `-Zbuild-std = ["core", "alloc"]`, `compiler-builtins-mem` and a JSON target | `-Zbuild-std` and `json-target-spec` are unstable. The pin keeps the unstable surface from moving under the build |
| D7 | Own workspace | The crate declares an empty `[workspace]` | The build needs a custom target and `-Zbuild-std`, so nothing else should inherit them |
| D8 | Linker layout | One `OVERLAY 0 : AT(0x1000)` block holding `.text` and `.data`; `.bss` and `.rodata` folded into `.data`; the first 16 bytes of data reserved | Code and data both start at offset 0 of their own segment, which `lld` refuses without an overlay. Windows writes heap and stack bookkeeping into the first 16 bytes of the data segment, and without the reserve the first string in the program was overwritten |
| D9 | Own packer in Python | `tools/ne_pack.py` reads the ELF and writes the NE file, with `tools/ne_dump.py` as an independent reader in the tests | No linker writes NE from `rust-lld` output. The packer is short, has no dependencies and is tested against a separate parser |
| D10 | Import stubs | Generated from a table of Wine's ordinals and signatures, checked against Wine's spec files | A hand-written stub per API is error-prone. The table is the one place a signature lives |
| D11 | Register discipline | Every stub and `export_proc!` saves EBX, ESI and EDI, clears the high half of ESP and reloads ES from DS | On Windows 3.11 and ME, BX is replaced by some calls, the high half of ESP can come back non-zero after a yield, and ES is not kept. Wine keeps everything, so it hid all three. See the pitfalls in the README |
| D12 | Entry point | `_start` calls INITTASK as its very first instruction, then `WaitEvent(0)` and `InitApp` | INITTASK reads registers the loader set. Instructions before it changed what it saw and killed the task |
| D13 | Fixup chains | The packer writes 0xFFFF into every non-additive fixup site | Windows follows the chain through the site; zeros made the loader walk to offset 0 and report "Insufficient memory to run this application" |
| D14 | Resource data | Lengths are padded to the alignment and raw data carries a 4-byte length prefix | Resource lengths are in alignment units, and a short file made a dialog silently fail to open |
| D15 | Single segments | One code segment and one data segment, with the 64 KB limits enforced in the packer. **Superseded by D18:** code may now fill several segments; the data segment is still one | Enough for the examples, and it keeps the packer small. Multi-segment code is not done |
| D16 | No Microsoft files | The repository ships no Windows files; testing on Windows 3.11 uses a tree the user supplies | The licensing is not ours to give |
| D17 | Verification | Examples are checked on Wine, on Windows for Workgroups 3.11 under DOSBox-X and on Windows ME in a virtual machine, never on real hardware | Wine tolerates mistakes real Windows rejects, so it is a smoke test. Real hardware, a 286 and Windows 3.0 remain open |
| D18 | Several code segments | The packer places code in up to 253 code segments (1, then 3 and up; the data segment stays 2) and does the relocating itself: `link.ld` links data at 0 and leaves each code section an output section of its own (`--unique`) with its relocations (`--emit-relocs`, and `--noinhibit-exec` for 16-bit jumps the linker cannot place), and the packer moves sections between segments and recomputes every reference to code | A linker script per placement (generated from a segments file, as Quill's T2 did) needs the placement before linking, so an automatic fill to a budget would need two links. With every section separate and every relocation kept, one link serves any placement, and a single-segment program comes out byte for byte as before |
| D19 | Placement | Pinned sections in segment 1 (entry, exported procedures, import stubs, `.text.w16fixed*`), then `.text.seg<N>` section names, then `place` patterns in a JSON segments file matched against demangled Rust paths and section names, then an automatic fill in link order to a budget (61,440 bytes by default), lowered and placed again when a segment comes out over 64 KB with its veneers | An attribute for the odd function, a small file for whole modules or crates, and nothing at all for a program that only needs to be bigger. JSON because the tools need no third-party Python and `tomllib` is 3.11 or later |
| D20 | Calls across segments | A direct call becomes a jump to an 11-byte veneer in the caller's segment that pushes a return trampoline in the callee's segment as the 4-byte return address and jumps far; the trampoline jumps far back. Tail calls and calls through function pointers into another segment go through a dynamic veneer that keeps the caller's CS:IP on a shadow return stack (256 entries by default) in the data segment, with a shared return trampoline at the same offset in every segment; a chain of tail calls reuses its entry | LLVM's `code16` output has no far calls, and the callee returns with a 4-byte near return. Per-site veneers keep no state, so recursion across segments is limited only by the stack, and no register changes, which matters because the Rust ABI here passes arguments in ECX and EDX. A dynamic return is unavoidable when the return address is not known where the jump is made |
| D21 | Function pointers, `dyn` and jump tables | Every address-taken function (a function's start referenced as an absolute address, from code or data) gets a 10-byte slot in a table at the same offset in every code segment, after 4 bytes of `int 3`; the program sees the slot's offset. Exported procedures keep their real address in segment 1. An address inside a function stored in data is a jump-table entry and moves with its function; one taken by code in another segment is refused, naming the symbol | A near pointer is only an offset, so it has to mean the same function from every segment. Jump tables stay on: `BIGSEG.EXE` checks a dense `match` on Windows 3.11, and the faults blamed on them elsewhere fit the dirty ESP of D23 |
| D22 | Load-on-call and discardable segments | Supported, off by default (segments are moveable and preloaded). Every far entry into such a segment goes through a gate in segment 1 that saves the 32-bit registers, moves to the 16-bit stack, loads the selector into ES so that Windows takes the not-present fault there, syncs the stack alias and returns far into the target | Taking the fault on a far jump from Rust code, with live 32-bit registers and the 32-bit stack, corrupted the program on Windows 3.11 (and, with the alias, made DOSBox-X abort). Through the gate, a segment discarded by `GlobalCompact` is reloaded and runs, in every run |
| D23 | A 32-bit stack for Rust | `_start` makes a 32-bit (B bit) alias of the stack segment with DPMI and Rust runs on it. Each import stub moves to the real 16-bit stack for its far call and back after it, `w16_sync_alias` moves the alias when Windows has moved the data segment, `export_proc!` moves to the alias when Windows calls in, and `w16_exit` frees it. Windows never runs on the alias | code16 addresses the stack through ESP, and an interrupt that returns to a 16-bit stack restores only SP: on Windows 3.11 in 386 Enhanced mode the high half of ESP becomes `8001` about 20 times a second, measured by `BIGSEG.EXE` at 5 to 7 times in a 4-million-iteration loop on the 16-bit stack and never on the alias. Cleaning ESP at API calls cannot cover a tick between two instructions, and a frame pointer copies the dirt. Making the task's own stack 32-bit (tried in the Liminal Installer) put KERNEL's code on it and faulted; switching per call keeps Windows on the stack it expects. Windows moved the data segment during `GlobalCompact`, hence the sync |
| D24 | Second reader for code | `tools/ne_check.py` decodes every code segment with `objdump` and fails on a near branch that leaves its segment or lands inside an instruction, or a far fixup that points inside one; CI runs it on every example | The packer rewrites machine code, so its own view of the result is not evidence. An independent decoder catches a wrong displacement, which a test of the packer's tables would miss |
| D25 | Windows 3.11 harness | `scripts/run-w31.sh` runs a program on a fresh copy of a Windows 3.11 tree the user supplies, under DOSBox-X (on the path or in a Docker image), as many times as asked, and counts the runs whose log ends `RESULT: PASS`; a stopped run leaves a screenshot | Faults on Windows 3.11 can be intermittent, so a single run proves little. A fresh tree per run keeps runs independent. It stays local: the repository cannot carry Windows |
| D26 | One packer for Quill and the Liminal Installer | This packer supersedes Quill's T2 packer (its D83), which both projects should vendor. Taken from Quill: kept relocations as the source of cross-segment references, a shadow return stack, slots at one offset in every segment, `R_386_PLT32` as a call, a size gate by segment budget, the `SEGMENT:OFFSET SIZE NAME` map and `ne_addr2sym.py`, and the decoding check (`check_segments.py`, extended here into `ne_check.py`). Changed: the packer places and relocates code itself instead of a generated linker script; direct calls use stateless per-site veneers and only tail calls and pointer calls use the shadow stack; cross-segment tail jumps (16-bit relative) are supported instead of refused; slots start at offset 4 instead of after the longest segment, so no segment is padded; the shadow stack is allocated by the packer; the data segment stays segment 2; segments may be moveable, load-on-call and discardable; and the 32-bit stack of D23 | Two incompatible packers would split every fix. Quill's design was proven on Windows 3.11 with a three-segment program; the changes remove its depth limit for ordinary recursion, its refusals of tail calls and its padding, and add automatic placement. Quill's open General Protection Fault in `rep stos` and `rep movs`, which moves with the stack and heap sizes, matches the dirty ESP of D23 and is expected to go with the 32-bit stack; its `segments.toml` globs become `place` patterns |
| D27 | NE library mode | `--library MANIFEST.json` writes a DLL: flags `0x8301` (library, Windows API, single data), a moveable data segment, `LibEntry` as `CS:IP`, stack 0 and `SS:SP` 0:0; exports are the manifest's names at fixed ordinals in segment 1 (gaps as unused bundles), `WEP` is ordinal 1 with a resident name and a default `mov ax, 1 ; retf 2` is added when the program has none; any `__w16imp_` symbol outside the manifest's allow-list (default the `KERNEL` `GlobalAlloc`, `GlobalLock`, `GlobalUnlock` and `GlobalFree`) fails the build. EXE output stays byte for byte the same | A host imports a DLL by ordinal, so ordinals cannot follow sort order. A library's code runs on a private stack (SS = DS), so a Windows call from it would run Windows on a stack it did not make, and a call that yields would let another task onto the same stack; the allow-list keeps a library compute-only. Single data gives every caller one DGROUP, which is what the export thunks load. Proving the output on a real loader (Windows 3.11, otvdm, Wine) needs the runtime and is the next change |
